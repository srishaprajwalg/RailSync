# RailVyuha

**Automatic Block Planning System**

**SIH Problem Statement:** SIH26027 — AI-Powered Automatic Block Planning to Maximize Asset Availability for Train Operations on Indian Railways.

## 1. Project Overview & Prototype Scope

RailVyuha is a prototype decision-support system designed to automate and optimize railway maintenance block planning. By transitioning from decentralized, manual maintenance scheduling (where Engineering, Signalling, and Traction departments request independent blocks) to an algorithmic approach, RailVyuha consolidates multi-department tasks and schedules them to maximize asset uptime.

**Current Prototype Scope:**
- **Corridor:** Bengaluru City (SBC) → Jolarpettai (JTJ) (~140 km, Double/Multiple Line). The prototype is strictly focused on this single demo corridor. Multi-corridor support is NOT currently implemented.
- **Time Horizon:** Simulates a continuous **30-day planning horizon**.
- **Data:** Uses synthetic/mock railway maintenance inputs (representing TMS/SMMS/TDMS) and operational data (timetable and goods-train forecasts). 
- **System Nature:** The current prototype is a decision-support/prototype system, not a production railway control system. It does not integrate with live railway databases or provide real-time railway control.

> **Important Disclaimer:** This is a prototype created for SIH26027 using simulated data and is not connected to live Indian Railways systems. Station chainage is computed via geographic coordinates rescaled to real total distance (145 km) and is an approximation of actual railway chainage. Goods-train forecasts and all TMS/SMMS/TDMS maintenance/defect data are fully synthetic. The metrics generated by this prototype are the results of a simulated maintenance scenario run against real passenger timetable data and do not represent validated real-world performance claims. External generative AI or LLMs are NOT powering the optimizer.

## 2. Implemented Architecture

The pipeline enforces strict separation between business logic, deterministic constraints, and presentation:

**Maintenance Data** → **Priority Assessment** → **Constraint/Safety Validation** → **OR-Tools CP-SAT Optimization** → **Coordinated Maintenance Block Plan** → **Dashboard Visualization**

### Backend (Python/FastAPI)
- **FastAPI API**: Exposes corridor data, timetables, and the optimization engine.
- **Data Engines**: Loads real station/schedule data (from `datameet/railways`) and generates synthetic maintenance/freight data.
- **Prioritization / Decision Logic**: An explainable, deterministic scoring model that evaluates defects, routine maintenance, severity, asset criticality, overdue days, and deadline urgency to generate an interpretable priority score (0-100).
- **Optimization Engine (OR-Tools CP-SAT)**: A single global spatiotemporal constraint model that simultaneously schedules tasks while respecting capacity across the entire corridor.
  - **Safety & Constraints**: Supports spatial separation, temporal conflict handling, safety margins, line/direction compatibility, cross-midnight scheduling, and maintenance task durations/deadlines.
  - **Consolidation**: Generates coordinated/consolidated work blocks where feasible.
  - **No LLMs**: The optimizer is strictly driven by the CP-SAT engine using exact mathematical constraints.

### Frontend (React/Vite/Tailwind)
The React-based dashboard visualizes the maintenance and scheduling pipeline clearly. 

**Current Dashboard Structure:**
1. **Data & Setup**: Manages maintenance requests/data, workflow/history, and task lifecycle/status handling.
2. **Optimized Action Plan**: Displays CP-SAT optimized maintenance blocks with readable dates/times, locations/chainages, task grouping/consolidation, and coordination/reasoning information where available. It includes a polished empty state when no blocks exist.
3. **Simple View**: An easy-to-understand operational visualization in Gantt format showing maintenance blocks and train operations with direction filtering.
4. **Technical View**: A detailed scheduling/constraint-oriented time-distance visualization.

**Planning Views:**
The dashboard supports **Month**, **Week**, and **Day** planning views. These views act as frontend time windows over the same generated planning result; switching views does not rerun the backend optimizer.

## 4. Important Prototype Limitations

- Uses synthetic/mock data.
- Strictly limited to a single corridor (SBC-JTJ).
- Prototype/demo scope only.
- No live railway database integration.
- No production deployment.
- No real-time railway control.
- Multi-corridor support is NOT currently implemented.
- External AI/LLM integration is NOT present in the scheduling logic.

## 5. Setup and Run Instructions

### Backend Setup

```bash
cd backend
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt # (fastapi, uvicorn, ortools, pydantic)
```

The backend expects the [`datameet/railways`](https://github.com/datameet/railways) data directory as a sibling of the repo root (i.e., `../railways/` relative to the project root). Override with the `RAILWAYS_DATA_DIR` environment variable if your data is elsewhere.

```bash
# Clone the data source (if not already done) — as a sibling of the project root
cd ..
git clone --depth 1 https://github.com/datameet/railways.git
cd RailVyuha/backend

uvicorn main:app --reload --host 127.0.0.1 --port 8000
```

### Frontend Setup

```bash
cd frontend
npm install
npm run dev
```

The frontend will be available at `http://localhost:3000`, and the backend runs on `http://127.0.0.1:8000`.
