# RailVyuha

**Automatic Block Planning System**

**SIH Problem Statement:** AI-Powered Automatic Block Planning to Maximize Asset Availability for Train Operations on Indian Railways.

## 1. Project Overview & Prototype Scope

RailVyuha is a prototype decision-support system designed to automate and optimize railway maintenance block planning. By transitioning from decentralized, manual maintenance scheduling (where Engineering, Signalling, and Traction departments request independent blocks) to an algorithmic approach, RailVyuha consolidates multi-department tasks and schedules them to maximize asset uptime.

**Corridor:** Bengaluru City (SBC) → Jolarpettai (JTJ) (~140 km, Double/Multiple Line).

### Data Sources

| Data Element | Source | Notes |
|---|---|---|
| Station list (7 stations) | **Real** — [`datameet/railways`](https://github.com/datameet/railways) `stations.json` | Names and codes are official Indian Railways data |
| Station chainage (km) | **Approximate** — rescaled Haversine | Cumulative Haversine distance rescaled proportionally to match the real SBC–JTJ route distance of 145.0 km (from official train 16519/16520 records in `trains.json`). Accounts for the ~10% curve and grade penalty in the Bangarapet–Kuppam–Jolarpettai hill section. |
| Passenger train schedules | **Real** — [`datameet/railways`](https://github.com/datameet/railways) `schedules.json` | Filtered to trains traversing 2+ corridor stations; missing intermediate stops are interpolated proportionally |
| Goods-train forecasts | **Synthetic** — `mock_data.py` | No public source exists for goods-train movement data |
| Maintenance tasks (TMS/SMMS/TDMS) | **Synthetic** — `mock_data.py` | No public source exists for maintenance defect/task data |

> **Important Disclaimer:** Station chainage is computed via geographic coordinates rescaled to real total distance (145 km) and is an approximation of actual railway chainage. Goods-train forecasts and all TMS/SMMS/TDMS maintenance/defect data are fully synthetic. The metrics generated by this prototype are the results of a simulated maintenance scenario run against real passenger timetable data and do not represent validated real-world performance claims.

## 2. Implemented Architecture

The prototype is currently implemented with the following stack and components:

### Backend (Python/FastAPI)
- **FastAPI API**: Exposes corridor data, timetables, and the optimization engine.
- **Real Corridor Data Engine** (`real_corridor.py`): Loads station and schedule data from the [`datameet/railways`](https://github.com/datameet/railways) public dataset. Computes approximate chainage via Haversine distance, classifies train types by name heuristics, infers Up/Down direction, and interpolates missing intermediate stops.
- **Mock Data Engine** (`mock_data.py`): A deterministic simulation generator that produces ~100 varied maintenance requests (Track, Signalling, Traction) and goods train forecast windows across the planning horizon.
- **Pydantic**: Enforces strict schemas for `Station`, `TrainSchedule`, `GoodsTrainForecast`, `MaintenanceTask`, and `PlannedBlock`.
- **AI Prioritization Engine**: An explainable, deterministic scoring model that evaluates defects, routine maintenance, severity, asset criticality, overdue days, and deadline urgency to generate an interpretable priority score (0-100).
- **Optimization Engine (OR-Tools CP-SAT)**: A task-specific spatiotemporal constraint model that replaces global line gap analysis and natively supports configurable planning horizons (Daily, Weekly, Monthly).
  - Configurable horizon lengths using absolute minutes from Day 0, scaling naturally for multi-day optimization.
  - Passenger train occupancy is interpolated at the task's relevant chainage.
  - Goods-train forecasts are modeled using conservative occupancy bounds.
  - Maintenance intervals are padded with a configurable safety margin.
  - CP-SAT strictly enforces no-overlap constraints between maintenance intervals and conflicting train occupancies.
  - **Explainable Task Statuses**: The engine distinctly categorizes tasks into `Planned` (scheduled), `Infeasible` (genuinely mathematically impossible due to hard constraints or train overlaps within deadline), or `Deferred` (feasible, but skipped due to capacity limits or lower priority).
  - **Objective Function Hierarchy**: A rigorous weighted lexicographic objective that:
    1. Maximizes the total number of feasible tasks scheduled.
    2. Prioritizes high-urgency tasks when capacity is limited.
    3. Prefers earlier execution, natively forcing compatible tasks to consolidate into shared block windows.

### Block Semantics
- A `PlannedBlock` represents a protected planning window.
- Its start and end chainages define the maximum spatial extent of the included tasks.
- **Important:** The entire range between those chainages should NOT be interpreted as continuously occupied by maintenance. The block protects discrete, localized tasks within that space.

### Frontend (React/Vite)
- **Dashboard**: A React-based interface utilizing Tailwind CSS v4, featuring a **Horizon Selector** (Daily/Weekly/Monthly) to drive the planning engine.
- **KPICards**: Displays real-time API-driven metrics tracking Task Processing (Planned/Deferred/Infeasible breakdowns), High-Priority handling, and verifiable Downtime Reduction.
- **CorridorTimeline**: A custom SVG Time-Distance graph that dynamically scales its grid and visually renders passenger train movements, maintenance blocks, and **freight train forecast uncertainty windows** across 1, 7, or 30-day horizons.
- **BlockPlan**: Lists the generated, consolidated multi-department blocks formatted relative to their horizon day (e.g., `Day 2 — 08:30`), complete with human-readable consolidation explanations.
- **TaskTable**: A comprehensive view of all incoming maintenance requests, displaying detailed AI priority logic explanations and explicitly translated execution statuses ("Feasible, but capacity allocated to higher-priority tasks" instead of just "Deferred").

## 3. End-to-End Workflow

1. The frontend fetches the corridor definitions (real stations), scheduled passenger timetables (real schedules), goods train forecasts (synthetic), and maintenance tasks (synthetic, prioritized by the AI engine).
2. The user selects a planning horizon (1, 7, or 30 days) and clicks "Generate Optimal Plan".
3. The frontend calls `POST /api/optimize` with the `horizon_days` payload.
4. The CP-SAT engine calculates exact spatiotemporal train overlaps, verifies standalone task feasibility, applies compatibility rules, and optimizes according to the lexicographic hierarchy.
5. The API returns the optimized blocks, detailed performance metrics, and a `task_statuses` mapping.
6. The dashboard updates to visualize the scaled Time-Distance graph, accurate KPIs, and detailed task execution states.

## 4. API Endpoints

- `GET /api/corridor`: Returns corridor stations with approximate chainage (derived from real data).
- `GET /api/timetables`: Returns passenger train schedules (derived from real data).
- `GET /api/goods_forecasts`: Returns synthetic goods train forecast windows.
- `GET /api/tasks`: Returns synthetic multi-department tasks with explicit priority logic.
- `POST /api/optimize`: Accepts `{ "horizon_days": int }`. Runs the CP-SAT optimizer and returns `{ blocks, metrics, task_statuses }`.

## 5. Validation Results

The CP-SAT constraint model and objective hierarchy have been rigorously verified against explicit operational test scenarios:
- **Spatial Separation** → **PASS** (Task schedules safely at the same time as a train, provided they are at different chainages).
- **Train Collision** → **PASS** (Task successfully rejected/pushed when its physical segment is occupied).
- **Safety Margin Constraint** → **PASS** (Tasks successfully respect the padded timeframe around train occupancy).
- **Lexicographic Capacity Allocation** → **PASS** (When capacity is limited, high-priority tasks are scheduled while low-priority tasks are strictly marked `Deferred`).
- **Safety vs Priority** → **PASS** (Safety constraints strictly override high-priority score weighting).

## 6. Limitations & Assumptions

The current system relies on the following operational abstractions and limitations:
- Station chainage is computed from geographic coordinates (Haversine), not official Indian Railways chainage.
- Uniform-speed interpolation is assumed between stations based on train type for missing intermediate stops.
- Goods-train forecast uncertainty is treated using conservative bounding (occupying the segment for the widest possible time).
- Maintenance tasks and goods-train forecasts are strictly synthetic.
- Prototype safety assumptions (e.g., safety margins, track-tamping compatibility matrices) are for demonstration and are not actual railway operating rules.
- The current spatial representation is an abstraction.
- No real integrations with TMS, SMMS, or TDMS exist yet.

## 7. Setup and Run Instructions

### Backend Setup

```bash
cd backend
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt # (fastapi, uvicorn, ortools, pydantic)
```

The backend expects the [`datameet/railways`](https://github.com/datameet/railways) data directory as a sibling of the repo root (i.e., `../railways/` relative to the project root). Override with the `RAILWAYS_DATA_DIR` environment variable if your data is elsewhere.

```bash
# Clone the data source (if not already done) — as a sibling of the project root
cd ..
git clone --depth 1 https://github.com/datameet/railways.git
cd RailSync/backend

uvicorn main:app --reload --host 127.0.0.1 --port 8000
```

### Frontend Setup

```bash
cd frontend
npm install
npm run dev
```

The frontend will be available at `http://localhost:3000` (or the port specified by Vite), and the backend runs on `http://127.0.0.1:8000`.
